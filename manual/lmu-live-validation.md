# LMU 실시간 진단 수집: 최소 실주행 검증

실시간 수집기와 랩 판정 신호 관측은 로컬 구현했습니다. Monza / GT3의 정상 기록 한 사례에서 실제 연결·파일과 실시간 기록 시간 일치·사용자의 게임 내 정상 기록 인정 확인을 마쳤습니다. 직접 스크린샷을 검토한 결과는 아니며, 컷/무효 사례와의 대조는 아직 남아 있습니다. 자동 결과는 계속 `valid=None`, `GAME_SCREEN_UNVERIFIED`입니다. `CONSISTENT_VALID_SIGNALS`는 정상 신호 일치 후보, `COUNT_POLICY_SIGNAL_OBSERVED`는 시간 집계 제한 신호, `INVALID_SIGNAL_OBSERVED`는 명시적인 랩 무효 신호 관측입니다. 모두 최종 유효/무효 판정과 구분합니다.

## 정상 랩 확인 절차

1. LMU에서 기존과 같은 **Monza / GT3 연습 세션**에 들어갑니다. 게임 설정과 telemetry 기록 설정은 바꾸지 않습니다.
2. [로컬 분석 화면](http://127.0.0.1:24176/)의 **실시간 진단 수집 → 수집 시작**을 누릅니다. `OBSERVING`이 되고 속도·페달 값이 현재 조작에 따라 변하는지 확인합니다. 연결 실패 사유가 나오면 그 문구부터 확인하며 추가 주행을 반복하지 않습니다.
3. 피트 출발 랩을 마친 다음 **정상 timed lap 한 번**을 완주합니다. 시작 중간에 연결된 랩과 피트 랩은 `UNKNOWN`이어도 정상입니다. 랩 종료 직후 scoring 갱신을 위해 몇 초 기다립니다.
4. 게임의 방금 완료한 랩 기록 화면을 남기고 분석 화면의 최근 랩 기록 시간·관측 결과를 함께 확인합니다. **수집 중지**를 누른 뒤 표시된 `recording_id`와 게임 화면의 랩 기록을 전달합니다. 화면에서 유효성이 계속 **미확인**인 것은 의도한 동작입니다.

현재 이 절차는 `2:05.798` 기록으로 한 번 확인했습니다. 사용자도 정상 기록으로 인정됐고 시간이 맞다고 확인했습니다. 컷·무효 표시가 없었다는 부분은 사용자의 회상이며 경고 전체를 직접 확인한 결과로 해석하지 않습니다. 한 번의 정상 timed lap은 연결·시간/랩 경계 대조용이며 차량/트랙 전체 지원이나 통계적 신뢰성을 검증한 표본은 아닙니다. 다음 사용자 작업은 아래 컷 표시 확인 한 사례입니다.

그 뒤 컷 시도 기록 `d60a971970034593870caa319a1670ac`도 수신했습니다. 게임 문구는 미관측입니다. 트랙 리밋 신호 `7→12`와 완료 뒤 `last_lap_time=-1`을 확인했지만 직접 무효 플래그는 `false`이고 관측 중단 근거도 있어 최종 판정은 `UNKNOWN`입니다. 현재 이 기록 때문에 즉시 재주행할 필요는 없습니다. 아래 절차는 이후 화면 판정 대조가 필요한 경우에 사용합니다.

## 정상 랩 대조 후 컷 표시 확인

정상 랩의 게임 기록과 JSONL 경계가 맞는 것을 확인한 뒤 다음 단계로 진행합니다.

코너 후보 비교·입력 반복성·수신 지연 진단을 포함한 최신 화면은 **`http://127.0.0.1:24176/`**에서 제공합니다. 이전 `24168` 서버는 종료·재시작 명령이 자동 승인 검토에서 정책 차단돼 유지했습니다. `24168`/`24169`/`24170` 모두 수집을 중지한 상태를 확인했으며 최신 수정본은 별도 프로세스에서 실행합니다. 다음 수집은 새 주소에서만 시작합니다.

정상 인정된 `2:05.798` 랩에서도 `count_lap_flag`가 일시적으로 `1`이 됐다가 `2`로 복귀했습니다. 이 신호를 누적해 랩 무효로 해석하던 처리를 수정했습니다. 제한 신호는 그대로 보존하고 중립적인 `COUNT_POLICY_SIGNAL_OBSERVED`로 분리합니다. 회복됐다는 이유만으로 유효 랩으로 자동 승격하지 않습니다. `lap_invalidated=true`도 실제 게임 표시와 대조할 별도 신호입니다.

1. 같은 연습 조건에서 다시 **수집 시작**을 누르고 새 랩의 시작 경계를 통과합니다.
2. 게임에서 트랙 리밋 경고 또는 랩 무효 표시가 발생한 사례를 한 번 남깁니다. 게임에 표시된 문구와 시점, 해당 랩 기록을 보존합니다. 경고가 곧 랩 무효라는 가정은 하지 않습니다.
3. 해당 랩을 마치고 scoring 갱신을 몇 초 기다린 뒤 **수집 중지**를 누릅니다. 정상 랩/컷 사례 각각의 `recording_id`와 게임 표시를 구분해 전달합니다.

개발 쪽에서 `mLapInvalidated`, 해당 랩의 `mCountLapFlag`, `mTrackLimitsSteps`, `mTotalLaps`, `mLastLapTime`, telemetry/scoring의 `mLapStartET`·시각을 함께 대조합니다. 다음 랩의 flag를 이전 랩에 붙이지 않고, 시점이 모호하면 `UNKNOWN`으로 남깁니다. 이 대조 뒤에도 피트 출입·중지/재연결·세션 변경은 별도 사례로 순서대로 확인해야 합니다. 사용자에게 한 번에 모든 사례를 요구하지 않습니다.

## 수집과 기록의 범위

| 항목 | 현재 동작 |
| --- | --- |
| 시작/중지 | 화면 버튼 또는 `POST /api/lmu/live/start`, `POST /api/lmu/live/stop` |
| 상태 조회 | `GET /api/lmu/live/status`. 조회·페이지 열기만으로 게임에 연결하거나 파일을 만들지 않음 |
| 브라우저 닫기 | 수집 작업은 서버에서 계속됨. **수집 중지** 또는 서버 정상 종료로 해제 |
| 기록 위치 | `logs/lmu-live/<recording_id>.jsonl` |
| 한 번의 수집 상한 | 900초(15분), 100000프레임, 128 MiB 중 먼저 도달하면 `LIMIT_REACHED`로 종료 |
| 데이터 최신성 | 기본 1초 이상 새 telemetry가 없으면 `STALE`로 현재 값을 숨김. scoring만 갱신돼도 telemetry 최신성을 연장하지 않음 |
| 포함 데이터 | 승인된 주행/판정 수치·bool, 이벤트 enum, 해시한 세션 키, 랩 관측과 근거 |
| 제외 데이터 | driver name, SteamID, 셋업 원문, SDK 전체 struct 원문, 게임 로컬 경로 |
| 보관 | 로컬 JSONL은 자동 업로드·자동 삭제하지 않음. 수집 상한은 누적 보관 폴더 전체 용량 제한이 아님 |

시작·중지·데이터 정체·연결 종료 근거는 `LIFECYCLE` 행에 기록합니다. 저장 실패나 미기록 샘플은 `journal_state=INCOMPLETE`로 표시하며 뒤의 기록이 성공해도 이전 실패를 지우지 않습니다. 이런 기록은 일부 근거가 빠졌을 수 있으므로 완전한 게임 판정 대조 자료로 간주하지 않습니다.

게임 종료·연결 실패·데이터 중단 이후 값은 현재 주행처럼 재사용하지 않습니다. 종료 대기 중인 연결 위에 새 수집 작업을 겹치지 않습니다. 중간 접속·피트·관측 gap·시계 역행·충돌·중단/재연결은 `UNKNOWN` 근거를 보존합니다. 데이터가 완전한 무효 랩과 데이터 누락으로 판단할 수 없는 랩은 서로 다른 경우입니다.

기존 DuckDB는 읽기 전용이며 새 JSONL 판정을 과거 파일에 소급 기록하지 않습니다. 게임 설정·공식 SDK 헤더·기존 iRacing 수집기·Claude의 오디오 작업 영역도 변경하지 않습니다.

## 수신 지연과 랩 관측 근거 확인

새 수집 기록은 `schema_version=2`입니다. 각 행에 증가하는 `sequence`, 수집 시작 이후의 `observed_elapsed_s`, UTC 시각인 `observed_utc`를 기록합니다. 정체 감지 시각은 실제 파일 저장이 늦어져도 감지 시점을 보존합니다. 최신성 판정과 간격 계산은 시스템 날짜 변경의 영향을 받지 않는 monotonic 시계를 사용합니다.

**수집 지연 진단**에서 마지막/최대 수신 간격, 새 telemetry 수신 간격, 게임 시간 간격, 현재 읽기 대기, 마지막 읽기 소요 시간과 마지막 정체 시점을 확인할 수 있습니다. 수집 종료 뒤 값은 종료 당시 값입니다. 게임 시간 간격이 짧더라도 로컬 수신 간격은 길 수 있으며 이 값만으로 게임 일시정지·전송·수집 처리 중 어느 쪽이 원인인지 확정하지 않습니다. 기존 JSONL에는 이 시각을 소급 생성하지 않습니다.

최근 랩의 **관측 근거·중단 사유**에는 시간 집계 정책 신호, 트랙 리밋 누적 신호, 명시적 무효 신호와 종료 scoring 확인 여부를 표시합니다. 양수 완료 시간이 제공되지 않으면 **기록 시간 없음**으로 표시하며 랩 경계 차이는 **공식 기록 아님**을 명시합니다. `UNKNOWN`인 랩에서는 정체·피트·부분 랩 등 관측 사유를 함께 확인합니다. 어느 표시도 게임의 최종 랩 유효성 판정을 대신하지 않습니다.

## 현재 검증의 한계

설치 SDK로 만든 x64 native bridge는 게임이 만든 mapping/event만 열고 기존 lock의 제한된 획득·복사·해제 절차를 사용합니다. 복사 전 배열/stream 길이를 검사하고, SDK/header/source/DLL fingerprint 불일치 및 양수가 아닌 `gameVersion`·연결 중 버전 변경을 거부합니다. 세션/시계 reset, 플레이어 ID/model·차량 부재 변화에서 캐시를 분리합니다.

최초 실행 게임 build의 호환성은 **`UNVERIFIED_INSTALLED_SDK_ONLY`**입니다. 설치 헤더의 크기·offset·packing과 양수 `gameVersion` 확인만으로 실제 실행 build의 ABI 호환을 확정하지 않습니다. 부재/lifecycle 변화를 관측하지 못한 같은 ID/model 재사용을 완전히 구분할 수도 없습니다. 합성 fixture·로컬 서비스/API/UI 시험은 실제 게임 연결·게임 화면 대조·온라인 운용 검증과 별개입니다.

native bridge가 필요한 PC에서는 설치된 게임의 `Support/SharedMemoryInterface` 헤더와 Visual Studio x64 C++ 빌드 도구로 로컬 빌드해야 합니다. 빌드·ABI probe는 게임에 연결하지 않습니다. 현재 PC의 브리지는 개발 과정에서 준비했으며 게임 업데이트 후 불일치 오류가 나면 주행을 반복하기 전에 브리지와 설치 헤더를 다시 확인합니다. SDK 헤더를 저장소에 복사하거나 배포하지 않습니다.
